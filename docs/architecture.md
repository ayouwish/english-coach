# 家庭英语口语教练 · 系统设计

> 版本 v1.0 ｜ 2026-10-22
> 用户：爸爸、妈妈、女儿（6–9 岁）｜ 形态：网页版先行 ｜ 部署：混合（云 API 为主 + 本地兜底）
> 配套文档：[接口契约](api-contract.md) · [部署手册](deployment.md) · [硬件与成本](hardware-cost.md)

## 0. 一句话结论

**网页版最大的架构红利是"登录即身份"。** 之前那份《家庭免唤醒语音助手方案》里最贵、最难、最容易翻车的两个模块
—— 声纹识别（谁在说话）和免唤醒介入决策（该不该接话）—— 在网页版里**直接消失**，
因为用户是登录进来的，系统天然知道面前是谁。这让第一版从"6 周起步的长期工程"压缩到
"2–3 周可用的产品"，而且零误触发风险。

代价是失去"随手说话就能练"的便利：必须主动打开网页。这在第一版是完全值得的取舍。

## 1. 需求与边界

### 1.1 三个用户，三套策略

| 用户 | 角色 | 水平 | 主要诉求 | 内容策略 |
|---|---|---|---|---|
| 爸爸 | parent | B1 | 商务/旅行场景能开口 | 完整音素级反馈 + 自由话题对话 |
| 妈妈 | parent | A2–B1 | 日常/亲子交流 | 完整音素级反馈 + 情景对话 |
| 女儿 | child | pre-A1/A1 | 敢开口、好玩、能坚持 | **不显示 IPA**，口型提示 + 单词级分数；20 分钟上限；儿童安全过滤 |

三个人的水平、动机、注意力跨度完全不同，所以**不是同一套界面换皮肤，而是两种交互模式**。

### 1.2 第一版做什么、不做什么

**做（V1 验收范围）**

1. 跟读评测：整句 / 单词 / **音素**三级分数，指出"你把 /θ/ 读成了 /s/"
2. **语调对比曲线**：你的 F0 vs 母语者 F0，标出"这里该升没升"
3. 日常对话训练：情景角色扮演，多轮，带温和纠错 + 可点击的标准答案
4. 错音本 + 间隔复习（SRS）：把错误变成排期表，而不是一次性分数
5. 家长面板：学习时长、趋势、高频错音 TOP10、女儿剩余时长
6. 三账号 + 儿童模式 + 全链路降级

**不做（明确记录，避免范围蔓延）**

| 不做 | 原因 | 何时再做 |
|---|---|---|
| 声纹识别 / 免唤醒介入 | 登录已解决身份问题 | 上常驻硬件设备时 |
| 全双工打断（barge-in）| 浏览器 AEC + 轮次检测复杂度极高；儿童反而喜欢"按一下说一句"的明确节奏 | M3 |
| 实时流式字幕 | 评测不是实时对话，3–6 秒反馈完全可接受 | 按需 |
| 移动 App / 原生端 | 网页版先验证教学闭环是否真的有用 | 验证后 |
| 中文教学 | 英语的 intonation 与中文的声调是两套技术问题 | 另立项 |
| 自建 GOP 音素引擎 | 云 API 效果更好且即时可用；自建是长期降本项 | M3，用 speechocean762 验证后再切 |

```
└───────────────────────────────────┬───────────────────────────────────────────────────────┘
                                    │ HTTP（同源，cookie 会话）
┌───────────────────────────────────▼───────────────────────────────────────────────────────┐
│  web 服务（Next.js :3000）—— 业务与账号，零模型密钥                                        │
│    认证/会话 · 语料与场景 · 练习记录 · phoneme_mastery · SRS 排期 · 家长面板 · 音频文件       │

│   │ local : faster-whisper 词级 + 停顿分析 + 文本比对（兜底，明确标注"单词级粗评"）      │    │

│   │ / mock          │  │ piper / mock                │  │ Qwen / Ollama），失败→模板   │   │
│   └─────────────────┘  └─────────────────────────────┘  └─────────────────────────────┘   │
└───────────────────────────────────────────────────────────────────────────────────────────┘
```

### 2.1 三条设计原则

**原则一：漏斗式降级，任何一层挂掉都能出结果。**

```
云 API 可用     → 音素级 + NBest + Prosody（最佳）
云 API 挂/超时  → local provider 词级分数 + 明确标注 warning，绝不假装精确
全都没了        → 录音与文本照常入库，页面提示"稍后可重试"，一条数据都不丢
```

**红线：绝不允许拿 ASR 置信度冒充音素级发音分。** ASR 的目标是"猜出你想说什么"（会自动纠错），
发音评测的目标是"忠实反映你实际发了什么音"（不能纠错）。这两件事在数学上就是矛盾的。
`local` 模式下的分数必须在 UI 上标注为"单词级（粗）"，宁可说"我不确定"，也不能给假精确。

**原则二：贵的模块放在最后，能缓存的全部预计算。**

跟读语料是固定的，所以**示范音频和参考 F0 曲线可以按 `(句子id, 音色, 语速)` 预生成一次、永久缓存**。
跟读闭环里最慢的 TTS 生成因此被移出关键路径，反馈延迟从 4–6 秒降到 1–2 秒。
`phoneme_mastery` 的更新用增量方式（每次练习只更新涉及到的音素），不做全表重算。

**原则三：AI 能力全部收口在 voice 服务。**

web 不持有任何模型密钥。这样：密钥只在一处、模型可整体替换、web 能在无密钥无 GPU 的机器上完整开发调试、
用量统计和限额有唯一入口。这是本设计里成本最低的一个决定，收益最大。

## 3. 核心流程

### 3.1 跟读闭环（产品的心脏）

```
选句 ──► 听母语者示范（缓存音）──► 跟读录音 ──► 提交
                                                   │
        ┌──────────────────────────────────────────┘
        ▼
   ┌─ 评测（并行）──────────────────────────────┐
   │ A. 发音评测：整句/单词/音素分 + NBest音素    │
   │ B. 语调：F0 曲线 + DTW + worst_regions      │
   └────────────────┬───────────────────────────┘
                    ▼
   ┌─ 反馈生成（LLM，失败走模板）───────────────┐
   │ 先说做对的地方 → 最多 2 个问题              │
   │ 每个问题：错在哪 + 为什么 + 口型动作 + 练习词 │
   │ 附 TTS 慢速示范 → 一键复读                   │
   └────────────────┬───────────────────────────┘
                    ▼
   落库：attempts / phoneme_scores → 更新 phoneme_mastery → 生成/更新 srs_cards
                    ▼
   界面：分数 + 单词热力图 + 音素高亮 + F0 对比图 + 反馈卡片 + 复读按钮
```

**教学原则（写进 prompt 的硬约束）：一次最多纠 2 个问题。** 一次纠 5 个错，学习者会崩溃，
这是语言学习产品的头号体验杀手。所以 `points` 数组在服务端就被截断到 2 条。

**闭环的关键是"复读"而不是"看分"。** 所以反馈卡片上的示范音按钮必须显眼，
复读后的第二次评分要与第一次并列显示（"第一次 41 分 → 现在 68 分"）。这个即时反馈循环才是练习的本质。

### 3.2 对话闭环

```
选情景（按年龄/水平过滤）──► 系统说开场白（缓存音 + 字幕 + 中文翻译）
                                    │
        ┌───────────────────────────┘
        ▼
   用户按住说话 ──► ASR 转写 ──► LLM（带情景 role_prompt + 水平 + 年龄）
        │                                    │
        │                    ┌───────────────┴────────────────┐
        │                    ▼                                ▼
        │              roleplay 回复                     温和纠错（可选强度）
        │              + 中文翻译                        grammar/vocab/politeness
        │              + TTS 播放                        + original→better
        │                    │                                │
        └────────────────────┴────────────────────────────────┘
                             ▼
              2–3 条"你现在的水平能说出口"的建议应答（点击即用）
                             ▼
                    轮次 +1，≥6 轮或场景完成 → 结束，写入 chat_sessions
```

**`suggested_replies` 是让 6–9 岁孩子开口的关键。** 孩子卡住时，空白的输入框会直接终结这个功能；
给三个可以直接说的短句，他挑一个念出来，对话就能继续。这是"降低开口门槛"，不是作弊。

### 3.3 延迟预算（push-to-talk 模式）

| 环节 | 目标 | 超限后果 |
|---|---|---|
| 录音结束 → ASR 出文本 | < 1.5s（local） / < 0.8s（azure） | — |
| 发音评测 | < 1.5s | 用户等待焦虑 |
| 语调（缓存参考音后） | < 0.8s | — |
| LLM 反馈生成 | < 3s | 会被感知为"卡" |
| **跟读反馈总计** | **< 4s** | 超过 6s 用户会离开页面 |
| 对话单轮（ASR+LLM+TTS首播） | < 4s | 孩子耐心 < 3s，故开场白与示范音全部预生成 |

> 对比：原声纹方案要求 TTFB < 800ms，因为那是**实时对话**。网页版是**回合制**，
> 3–4 秒完全可接受 —— 这是拿掉全双工换来的巨大工程简化。

## 4. 技术选型

| 层 | 选择 | 主要备选 | 选择理由 |
|---|---|---|---|
| 前端 | Next.js 15 App Router + TS + Tailwind | Vite+Express、Remix | API routes 与页面同一个部署单元，三个人的自用项目不该有两个前端进程 |
| 数据库 | SQLite（better-sqlite3 + Drizzle） | Postgres、MySQL | 3 个用户、单机部署。SQLite 是**更多**而不是更少的选择：零运维、单文件备份、够快 |
| 认证 | cookie session + argon2 | NextAuth、JWT | 三个账号不需要 OAuth 生态，少一层依赖少一个故障点 |
| 发音评测 | **Azure AI Speech Pronunciation Assessment** | 讯飞 ISE、SpeechSuper、自建 GOP | 目前唯一把"哪里不对"结构化返回的 API：音素级分数 + `NBestPhonemes`（你实际发成了什么音）+ Prosody |
| 语调 | **自建 F0 + DTW（parselmouth）** | Azure ProsodyScore | Azure 只给整句一个分和 `Monotone` 标记，**知道"语调平"但不知道"哪里该升没升"**；自建零成本、离线可用、能画出对比曲线 |
| ASR 兜底 | faster-whisper | SenseVoice、Parakeet | ctranslate2 后端，不依赖 torch，CPU 可跑，中英混说可用 |
| TTS | Azure Neural / edge-tts / Piper | ElevenLabs、CosyVoice2 | 教学需要 SSML：慢速、重音强调、单音素朗读 —— 这是小 TTS 做不到的 |
| LLM | OpenAI 兼容（DeepSeek / Qwen / Ollama 均可） | 各家专属 SDK | 一个接口三种部署（云/本地/离线），换模型不改代码 |
| 音频解码 | PyAV | 系统 ffmpeg | PyAV 自带 ffmpeg 库，容器和主机都不需要额外装系统包 |
| 编排 | docker compose + Caddy | 裸机 systemd、k8s | k8s 在三个人的自用项目里是纯负债 |
| HTTPS | Caddy | nginx + certbot | 自动证书。**麦克风必须 HTTPS**，这不是可选项 |

### 4.1 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 纯前端 + Web Speech API | 它只给识别文本，**给不出任何发音分**；且 Chrome 的实现依赖云端，离线不可用 |
| 用 LLM 直接听音频评发音 | LLM 没有音素级声学后验，只能说"听起来还不错"，无法定位到具体音素，更无法追踪进步 |
| OpenAI Realtime 全双工 | 音频 token 昂贵、中文反馈可控性差、**它同样不返回音素级诊断**；且成本随使用时长的增长是线性的 |
| 直接买 Duolingo / ELSA | 无法自定义内容、无法追踪自家孩子的音素进步、儿童与成人混用同一策略、数据在别人手里 |
| 一次到位做常驻语音设备 | 用户已明确"先要网页版"。且常驻设备需要真实家庭数据持续调优（见原方案 M2/M3），先证明教学闭环有用再投入 |

## 5. 数据模型：护城河在 `phoneme_mastery`

完整 schema 见[接口契约第 10 节](api-contract.md)。这里只说设计意图：

```
attempts ──1:N──► phoneme_scores        （每次练习的原始事实）
                        │
                        └──聚合──► phoneme_mastery   （★ 长期价值）
                                        user_id + phoneme
                                        attempts / avg / best / last / trend_30d
                        │
                        └──派生──► srs_cards         （把错误变成明天的任务）
```

**单次评分任何 App 都能做。** 但"追踪女儿 /θ/ 这个音三个月从 41 分涨到 68 分，并据此安排今天的练习"，
是只有长期自用才能积累、也最不可替代的东西。所以 V1 就必须落库，哪怕界面只是一个列表。

家长面板的价值也全部来自这里：它回答的是"我女儿到底有没有变好"，而不是"她今天点了几个按钮"。

### 5.1 间隔复习（简化 SM-2）

| 评分 | 含义 | 下次复习 |
|---|---|---|
| again | 还是读不对 | 当天（10 分钟后） |
| hard | 勉强对了 | 1 天 |
| good | 读对了 | 3 天 |
| easy | 很轻松 | 7 天 |

卡片粒度为**音素**（不是单词）：因为要练的是 `/θ/` 这个发音动作，而不是 `think` 这个词。
练习时把该音素出现在不同单词里的例子轮换给用户，这才是发音训练。

### 5.2 如何证明"真的有效"（唯一诚实的指标）

每周一次**盲测**：同样的 10 句话，**全程不给任何反馈**，与上周对比。
平时的分数因为存在"看反馈后重读"的即时提升，不能用来证明长期进步。
没有盲测，这个 App 就只是让人感觉良好。

**盲测有一条不显眼但致命的实现要求：进行中绝不能返回分数。**
用户一旦看到分数就会立刻重读，盲测随即失效——而且这种失效是**静默的**，日志里看不出任何异常，
只会让你几个月后得出"孩子没进步"的错误结论。所以：

| 要求 | 理由 |
|---|---|
| 盲测进行中，接口只返回 `{attempt_id, blind:true, progress}`，**不含 result/feedback/scores** | 防止即时模仿污染测量 |
| `is_blind=1` 的记录**不参与** `phoneme_mastery` 聚合、练习趋势与 SRS 排期 | 否则两套指标互相污染，两个都失效 |
| 抽题从**该学习者练过的语料**里抽、且每次固定同一组 | 没学过的测不出水平；换题就无法与上周比 |

这三条已写进[接口契约 §13.3](api-contract.md)（功能正确性要求，非 UI 偏好），并由
`tests/e2e_full.mjs` 独立验证。

### 5.3 从数据到教学：薄弱音素诊断 → 口型微课 → 强化练习

`phoneme_mastery` 如果只是躺在数据库里，就只是一个数字；这一节是把它变成**教学动作**的闭环：

```
历史评测（phoneme_scores）
   │  聚合：样本≥2 才统计（1 次的噪声太大）
   ▼
薄弱音素诊断（/api/diagnosis）
   │  weak(<65) / watch(65–80) / ok(≥80) + 近 3 次趋势 + 关联错误词
   ▼
口型动画微课（ArticulationDemo + lib/articulation.ts）
   │  参数化侧面剖面：舌位/唇形/气流/声带/鼻腔 + 循环教学动作
   │  同一套参数可**自动对比两个音**（/θ/ 与 /s/ 的差别就是"舌尖是否伸出齿间"）
   ▼
强化练习队列（/practice?focus=<音素>）
   │  从 300 句语料里筛含该音素的句子，**最小对立对优先**
   ▼
回到诊断看趋势变化（真正的闭环）
```

**为什么把口型做成"参数化渲染"而不是逐个手绘：**
43 个音素逐个画 SVG 既不可维护、也无法自动生成。抽象成 10 个可比较的维度
（舌位高低/前后、唇开合/圆展、气流强弱、受阻位置、声带振动、是否鼻音、时长）之后，
**同一个渲染器能画任意音素**，还能用参数差异自动解释"这两个音差在哪"——
这才是"自动制作教学材料"的关键：内容由参数表决定，渲染是纯函数。

**为什么不做"自动抓第三方视频"**：运行时去抓教学视频会带来版权、画质不可控、
**儿童不宜内容**与外链失效问题；给 6–9 岁孩子用的东西不该赌这个。参数化动画零版权、
可离线、可无限复制、可循环慢放与对比，性价比更高。真人嘴部画面需要素材（家长自拍或精选授权），
属于**可选增强**，不是自动化能解决的。

**儿童可见性**：诊断页是儿童可访问页，因此儿童版只用 `childLabel` / `tipChildZh` / 例词，
**不出现任何 IPA 符号**；`/report` 已纳入 `check:child-ipa` 守卫（含 RSC 负载全量扫描）。

## 6. 儿童模式（6–9 岁）

这不是"字号调大"，是另一套交互假设。

| 维度 | 成人模式 | 儿童模式 |
|---|---|---|
| 分数呈现 | 音素热力图 + IPA 符号 | **不显示 IPA**（抽象符号对 6–9 岁无意义），用口型提示 + 示范音 |
| 主反馈 | 分项分数 + 曲线 | emoji 星级 + "这个音再试一次" + 一键听示范 |
| 对话门槛 | 可自由输入 | **建议应答点击即用**，可语音回答 |
| 时长 | 自己控制 | 硬上限（默认 20 分钟，家长可调；见 `daily_limit_minutes`），到点友好收尾并给奖励动效 |
| 内容 | 全场景 | 按 `min_age` 过滤 + `child_safe` prompt + 输出关键词兜底过滤 |
| 语气 | 直接 | 必须鼓励，不得出现批评性词汇（服务端 prompt 硬约束） |

**安全是三道防线，不是一道：**
1. 场景准入：`chat_scenarios.min_age ≤ 孩子年龄`（数据库层过滤）
2. Prompt 约束：`learner.age_band == "child"` 时服务端注入儿童安全 system prompt
3. 输出兜底：对 LLM 返回文本做关键词过滤，命中则替换为安全内容并置 `flag=unsafe_filtered`

儿童语音数据额外谨慎：默认只保存练习所需音频，家长面板可一键删除，见第 8 节。

## 8. 隐私与安全

1. **密钥只在 voice 服务**，web 与浏览器都不持有；`.env` 不入库，`deploy/.env.example` 只放占位符。
2. **音频默认只存练习片段**，落在 `data/audio/`，不入数据库；提供"删除我的所有语音"入口。
3. **儿童数据更严格**：家长面板可查看、可删除；不做任何外部分享；不接入任何第三方分析 SDK。
4. **上云边界清楚**：只有用户主动点击练习产生的音频会送到云 API；没有常驻监听，没有后台录音。
   （这正是网页版相对常驻设备的最大隐私优势 —— 麦克风只在用户按下时打开。）
5. **可审计**：`audit_log` 记录敏感操作（登录、删除、家长查看）。
6. **数据库与音频目录都在自己家里**，备份 = 打包 `data/` 一个目录。

### 10.1 已关闭的关键风险：音素符号空间

**问题**：`focus_phonemes` 是 `srs_cards`（phoneme 卡）的 key，也是口型提示的映射依据。
语料最初按英式 RP 标注（`ɒ ɑː ɔː ɜː iː uː ʊə eə ɪə`），而本产品全链路目标是 **en-US**。
两边不在同一符号空间时，同一个发音错误会生成**两张不同的卡片**，
`phoneme_mastery` 的长期追踪会在部分音素上**静默断裂**——不报错，只是数据悄悄失去意义。

**解法（三层，已落地）**：

| 层 | 做法 | 位置 |
|---|---|---|
| 规范空间 | 定义 `canonical-v1`：把 `ɹ→r ɛ→e ɝ→ɜ ɚ→ə ɒ→ɑ iː→i uː→u oʊ→əʊ` 等折叠到单一符号集（43 个） | `voice/app/phonemes.py` |
| 运行时 | provider 输出在边界处一律归一到规范空间；未覆盖符号**原样返回并打 WARNING**（不丢信息），可用 `seen_unknown_phonemes()` 取全集 | `voice/app/api.py` |
| 语料 | 300 句 `focus_phonemes` 全部归一到规范空间（115 处自动归一 + 27 处人工修正）；3 个 en-US 不存在的央化双元音改为句中真实音素 | `web/src/data/sentences.json` |

**关键洞察：这件事不必等 Azure 联调。** 规范空间是我们自己定义的，voice 会把**任何** provider 的输出折叠进来；
只要语料也用同一空间，两边就永远一致，无论云端吐什么符号。

**四道守卫（都可复跑，且都做过变异测试证明会失败）**：

| 守卫 | 命令 | 挡什么 |
|---|---|---|
| 语料符号与真实性 | `voice/.venv/bin/python tests/audit_corpus_phonemes.py` | 用 CMU 词典做真实 G2P：A 类"不在规范空间"、B 类"标注的音素在句中不存在" |
| 语料格式 | `node web/scripts/validate-corpus.mjs` | 条数/重复/长度/最小对立对/退役符号 |
| 提示表覆盖 | `pnpm check:phoneme-hints` | 规范集新增符号而提示表漏配 → 直接红 |
| 儿童 IPA 泄漏 | `pnpm check:child-ipa` | 把儿童可见的**整个响应/整页 HTML（含 RSC 负载）序列化后扫描**全部特征字形 |

> 儿童 IPA 泄漏在这个项目里出现过**三次**：`srs_cards.id` → `hint_key` → `demo_text`。
> 逐字段打补丁挡不住第四次，所以最终形态是"整体序列化扫描 + 运行时递归兜底（`childSafeDeep`）"两层。

### 10.2 其余已知限制（诚实清单）

| # | 限制 | 影响 | 计划 |
|---|---|---|---|
| 1 | 家长面板只读 | 无法建号/改密码，账号靠 seed 或 `BOOTSTRAP_*` | V2 按需 |
| 2 | 每日时长只按累计分钟判断 | 未处理跨零点与并发竞态 | 可接受（3 人自用） |

| 5 | 缓存无分布式锁 | 多 worker/多容器共享 `DATA_DIR` 时同一 key 可能各生成一次 | 单进程部署下无影响；要 scale out 应先改架构而非打补丁 |

| 7 | `u ʊ ɑ ɔ ʌ` 等 25 个规范符号**有意不给口型提示** | 这些音素的卡片文案退化为通用鼓励语 | 现有 17 个提示键里没有贴切的；硬套会误导。若要覆盖需按契约流程新增提示键 |

## 12. 两条给未来的工程教训

这份方案里最值钱的不是代码，是两次"静默错误"的教训——它们的共同点是**不报错，只是让数据失去意义**：

1. **缓存/去重的 key 必须包含所有影响产物的身份分量。**
   `cache_key(text, voice, rate)` 看着完备，但 `voice` 的默认值在三种 provider 下是同一个字符串，
   于是 mock 生成的合成音会被 azure 命中。**每写一个 key，都要问"还有什么会改变这个产物"。**

2. **一个约束如果只靠"逐处检查"维持，它一定会被绕过。**
   儿童不得见 IPA 这条约束，在这个项目里从三个不同路径漏出去过：`srs_cards.id` → `hint_key` → `demo_text`。
   最终有效的形态是**结构性防护**（运行时递归兜底 + 整页序列化扫描守卫 + 变异测试证明守卫会失败），
   而不是继续打第四个补丁。
